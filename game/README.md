# 示例 FPS —— 跑在 PhysEngine 上的游戏

这个目录里的东西**不是引擎的一部分**。它是引擎的使用者：`physengine` 一行都不知道
它的存在，也不含任何渲染或输入代码（见 `ARCHITECTURE.md` §2 与 §6）。

```
bash scripts/build.sh          # 构建（引擎 + 测试 + demo + 游戏）
build/bin/pe_game.exe          # 有控制台就交互玩，没有就机器人自动打
```

| 参数 | 作用 |
|---|---|
| `--play` | 强制交互模式 |
| `--script` | 强制机器人模式（CI / 复现用） |
| `--no-color` | 关掉 ANSI 颜色 |
| `--frames N` | 只跑 N 帧就退出（冒烟测试用） |

**操作**：`W/A/S/D` 移动，`Q/E` 或左右方向键转向，上/下方向键抬低头，
`Shift` 冲刺，`空格` 跳跃，`Ctrl`/`F`/鼠标左键开火，`R` 换弹，`Esc` 退出。
**一局结束后**（阵亡或清场）停在结算画面上：`R` 重开一局，`Esc` 退出。

**目标**：清掉地图上 5 个敌人。

---

## 渲染器就是一层 `world.Raycast()`

这是整个游戏里最值得看的一件事：`game/Renderer.cpp` **没有任何自己的几何数据** ——
没有网格、没有顶点缓冲、没有场景图。屏幕上每一个字符就是一次物理引擎的射线查询：

```cpp
for 每个像素 (x, y):
    dir = 由相机朝向和像素位置算出的方向
    world.Raycast({eye, dir}, hit, kVisionMask)   // 引擎干活
    按 hit.distance 选字符、按 hit.body 是谁选颜色
```

这么做有两个好处，都不是"取巧"：

1. **它自动就是正确的 3D**。台阶、不同高度的箱子、半人高的掩体、站在高台上的敌人
   —— 全都不需要任何特殊处理，因为射线打的是真正的三维几何。经典 Wolfenstein 式
   渲染器只投影一根水平射线、假设墙都一样高，上面这些它一个都画不出来。

2. **画面里看到的就是物理里存在的**。渲染和碰撞用同一份数据、同一个查询函数，
   不存在"看着能过去实际撞墙"这类渲染与物理不一致的 bug。

实测 100×34 的画面 = 3400 条射线/帧，**渲染 3.4 ms + 物理 0.08 ms**，
上限约 290 fps。

真接了 GPU 渲染之后，把 `Renderer.*` 整个换掉即可：引擎已经提供
`GetDebugDrawData()`（每个碰撞体的形状 + 世界位姿）和
`GetInterpolatedTransform(handle, world.Alpha())`（固定步长物理配可变帧率渲染
必须用它，否则画面会抖）。

## 引擎的哪些能力被用到了

| 引擎能力 | 游戏里的用途 |
|---|---|
| `PhysicsWorld::Raycast` | **渲染每一个像素**、hitscan 开枪、敌人 AI 的视线判定 |
| `CharacterController` | 玩家和敌人的移动（贴墙滑行、上台阶、走斜坡） |
| 运动学替身刚体 | 让世界"看得见"角色：触发区能检测、箱子能被推 |
| 层掩码 | 开枪不打到自己、敌人不打队友、渲染射线穿透触发区、**碎块看得见但不挡路** |
| 触发器 + 事件队列 | 补血/补弹药的拾取区 |
| `ApplyImpulseAtPoint` | 子弹把箱子打飞、打转 |
| 动态刚体 + 求解器 | 可推动的箱子、叠起来的箱堆、**打碎箱子飞出来的碎块** |
| 运行时创建/销毁刚体 | 箱子碎成八块、碎块到寿命自己消失 |

## 开枪的反馈：曳光弹、火花、碎块

hitscan 武器的子弹是**瞬时**的：一条射线、一个结果，世界里没有任何东西飞过。
如果不专门画点什么，开一枪在画面上就只有角落里的弹药数变了一下 —— 玩家的
主观感受是"这枪好像坏了"。所以有这四件事，每一件都在回答玩家的一个问题：

| 特效 | 回答的问题 | 实现在哪 |
|---|---|---|
| 枪 + 手 + 枪口焰 + 后坐 | 我开火了吗 | `PixelRenderer::DrawWeapon` |
| 曳光弹 | 这一枪打到哪儿去了 | `Game::SpawnTracer` -> 渲染器投影成线 |
| 命中火花 | 打中了什么材质 | `Game::SpawnImpact`，颜色按 `EntityKind` |
| 准星命中标记 | 打中的是不是敌人 | `Game::HitMarker()` |

**敌人开枪也画曳光弹**（红色）。这不是装饰：第一人称视野只有 60 度，大部分
火力是从画面外打过来的，那条红线是玩家判断"威胁在哪个方向"的唯一线索。

特效数据存在 `Game` 里而不是渲染器里，因为字符版、像素版、无头截图模式画的
是**同一批**火花，而且它们的寿命按游戏时间走。渲染器只负责把世界坐标投影到
屏幕上（`ProjectToScreen()`，两个渲染器共用）。

### 手里那把枪：整把枪只由一条轴决定

第一人称里枪是朝着屏幕**里面**指的，投影出来必然是一条又斜又收窄的形状。
第一版用轴对齐矩形拼的，枪管只能横躺在画面底部 —— 那不是"端着一把枪"，
是"举着一把横过来的枪"。

所以加了一个图元 `DrawTaperedBar()`（从 A 点宽 w0 画到 B 点宽 w1），然后整把枪
挂在一条轴上：后膛在右下角、故意伸出画面外（枪托本来就抵在你自己肩上，
不该出现在视野里），枪口在准星右下方一点。机匣 → 护木 → 枪管沿轴依次变细，
这就是透视；准星座和照门立在枪身上方，连成的线正好指着准星；两只手一前一后
握着 —— 没有手的枪看着像浮在屏幕前的一张 HUD 贴图。

**大小是一个数**：`PixelRenderer.cpp` 里的 `kWeaponScale`（现在是 `0.66`）。
所有长度、宽度、偏移都按"满尺寸像素"写，最后统一乘它，所以调大调小不会把比例
调歪（手比枪大、弹匣比机匣宽之类）。缩放的锚点是**后膛**不是枪口 —— 枪是从
右下角伸进来的，缩小就该往那个角上收；锚在枪口的话，缩小会把后膛拽到画面中央，
变成一把飘在屏幕正中的小枪。

两个不显眼但决定成败的细节：

- **斜条的宽度要做换算**。`w` 是垂直于轴的宽度，而水平扫描线切出来的那一段比它
  长 `L/|dy|` 倍。漏掉这一步的症状是"越斜的零件画得越细"，一把 35 度的枪会瘦掉
  五分之一，看着像根木板。
- **要描边**。场景是暗的、枪也是暗的，不描边枪身会和地板糊在一起，只剩高光那
  一条线看得见。低分辨率的东西要读得出形状，靠的是轮廓。

枪口焰也跟着这条轴：沿枪管方向拉长、垂直方向收窄、而且**只朝前喷**。
对称的一团光看着像枪口上挂了个灯泡。

### 箱子是真的碎，不是播动画

打够三枪，箱子从世界里被删掉，原地换成**八个小刚体**（2×2×2 切分，合起来
正好是原来的体积）。之后就没有任何"破碎系统"的事了 —— 碎块是普通的动态刚体，
会飞、会翻滚、会互相碰、会叠在地上，全部由求解器负责。这也是它看起来对的原因：
它本来就是真的。

两个必须自己管的地方：

- **寿命和预算**（`debrisLifetime` / `debrisBudget`）。不回收的话，打上十分钟
  地上会躺着几百个刚体，宽相位和求解器都要为此买单。特效永远不该让帧率掉下去。
- **碎块单独一层**（`kLayerDebris`）。它在渲染掩码里、不在任何一个射击/角色
  掩码里，于是"看得见、但不挡路也不挡枪"。一地木屑把玩家卡住、或者飞过眼前的
  碎屑吃掉子弹，都是特效反过来毁掉手感的经典例子。

## 几个玩法上的设计决定

**角色不是动态刚体**，玩家和敌人都不是 —— 理由见
`include/pe/character/CharacterController.h` 顶部。简单说：动态刚体会被箱子撞飞、
爬不上台阶、贴墙抖，手感完全不可控。它们各自是一个 `CharacterController`
加一个**运动学替身刚体**（`invMass = 0`），于是"能推动箱子、箱子推不动它"
这条 CS 手感约定不需要写任何特判 —— 求解器天然就是这个行为。

**敌人走路是胶囊，身体是人形**。这两件事本来就是两个东西，以前只是恰好用了
同一个形状：

- **移动**用 `CharacterController` 里的胶囊，而且只能是胶囊 —— 圆柱侧面才贴得住墙、
  圆底才上得去台阶和斜坡。换成人形立刻卡门框、卡楼梯，这也是各家引擎的角色
  控制器至今只给胶囊的原因。
- **世界看见的**是运动学替身刚体上挂的碰撞体：射线渲染、玩家开枪、AI 视线判定
  全问它。它没有任何理由必须是胶囊。

所以只换后者：七块碰撞体拼一个人形（头一个球 + 躯干/胯/两腿/两臂六个盒子），
局部 +X 是正面，朝向由替身刚体的旋转给 —— 敌人会**限速转身**看向你，
那是从掩体后探头时唯一的预警。渲染器按碰撞体的局部高度换色（头=肤色、
躯干=红、腿=暗红），低分辨率下这点色差就够让人形一眼读出来。

代价是**敌人从 0.76 米宽的胶囊变成了 0.37 米宽的躯干**，明显更难打。机器人为此
改了两处，两处都是原来那套判据被形状变化证伪了：开火阈值从一条经验公式换成
几何量 `atan(躯干半宽 / 距离)`（"偏差已经小到子弹落在轮廓里"），以及**开枪前
先停下侧移** —— 5.5 m/s 的侧移在 1/30 秒里就把自己挪出 18 厘米，九米外是 1.2 度，
比躯干张开的角还大，误差主要是自己造成的。改完之后机器人 15 枪清场、
零脱靶（原来是 8.9 秒清场，现在 6.8 秒）。

**敌人有反应时间**（`enemyReactionTime = 0.5s`）。没有它，敌人一进视线就是瞬发命中，
玩家从拐角探头会毫无预兆地掉血，主观感受是"被作弊了"。这是公平性，不是难度调节。

**敌人出生点刻意让它们看不见玩家**。第一版把敌人放在同一个房间，玩家还没转过身
就先掉 18 点血，而且开火的敌人根本不在视野里。玩家得先看见威胁，才轮到威胁看见玩家。

**关卡尺度是为渲染器设计的**。第一版做了个 52×36 米的大广场，画出来四分之三
是地板 —— 几何上完全正确，但看着像在停机坪上走。光线投射的画面好不好看，取决于
"视线多久会撞到一堵墙"，所以改成 34×26 米、被隔墙切成四个房间加中央走廊。

**机器人是会瞄准的，不是一段固定脚本**。第一版是时间轴脚本（"第 3 到 6 秒边走边
开火"），它能跑，但打不死任何人 —— 瞎打的，结果永远是"还剩 5 个敌人，你阵亡了"。
换成会瞄准之后，无人值守跑一遍会真正走完整条链路：发现 → 转向 → 开火 → 命中 →
击杀 → 换弹 → 推进 → 清场。这样它才既是演示、又是有意义的冒烟测试
（`ctest` 里的 `pe_game_smoke`）。

## 曾经的一个崩溃：走过弹药箱就闪退

拾取物的标准写法是"在 `OnTriggerEnter` 里把自己销毁掉"，引擎也明确承诺
回调里增删物体是安全的（事件在 `Step()` 末尾统一派发，见 `Events.h`）。
但**销毁碰撞体会往正在派发的那个事件队列里补发 Exit** —— 而当时的派发循环
是 range-for，队列一扩容，缓存的 begin/end 就成了野指针，接着往下走。

表现是"往前走几步就闪退"：玩家先挨了几枪，然后踩到出生点旁边两米的补血包，
进程直接没了。崩溃点在引擎内部，离真正的原因隔着好几层调用栈。

修在 `src/scene/TriggerSystem.cpp`（下标遍历 + 按值取事件），回归测试是
`tests/test_world.cpp` 里的"回调里销毁触发器本身也是安全的"。

另外图形模式当时**没有结算横幅**：被打死之后画面一停、窗口就关了，
和崩溃在观感上完全一样。现在会显示 `YOU DIED` / `MISSION COMPLETE`。

**而且死了不该只能重启程序。** 死亡在 FPS 里是常态而不是一局的终点，所以结算
画面会停下来等一个决定：`R` 重开、`Esc` 退出。重开的做法是整个换一个新的
`Game` 对象，而不是写一个 `Reset()` 挨个把成员清回去 —— 后者的失败模式是
"漏了一个成员"，而漏掉的偏偏是最难发现的那种（上一局的碎块还躺在地上、
敌人的警觉状态还留着）。重新构造则不可能漏，编译器负责。

两个容易踩的地方，都在代码里写了注释：
- **`previous` 时间戳必须重置**。玩家在结算画面上待了十秒，不重置的话新一局
  第一帧的 dt 就是十秒，角色会被直接弹出地图。
- **等按键要先看到松开**。`R` 同时是换弹键，死的那一刻手里多半正按着它 ——
  不做这个"上膛"判断，结算画面会一闪而过，看起来又像闪退。

机器人模式（`--script`）不参与这套：它亮两秒结算画面就退出，否则 CI 会挂住。
