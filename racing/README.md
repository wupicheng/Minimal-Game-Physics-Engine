# 示例赛车 —— 跑在 PhysEngine 上的第二个游戏

和 `game/` 那个 FPS 一样，这个目录**不是引擎的一部分**：`physengine` 一行都不知道
它的存在。两个游戏之间也没有任何依赖，只共用 `platform/`（窗口 + 画布）。

```
bash scripts/build.sh            # 构建（引擎 + 测试 + 两个游戏）
build/bin/pe_racing.exe          # 开窗口自己开
build/bin/pe_racing.exe --bot    # 机器人跑完整场，打印圈速（CI 用）
build/bin/pe_racing.exe --shot out.ppm --at 9   # 无头截图，第 9 秒那一帧
```

**操作**：`W`/`↑` 油门，`S`/`↓` 刹车（停住后继续踩 = 倒车），`A`/`D` 或 `←`/`→`
转向，`空格` 手刹漂移，`R` 复位，`Esc` 退出。完赛后 `R` 重开。

**目标**：跑完 3 圈。跳台在上方直道**外侧** —— 想飞就往外压一点，赶时间就直接过。

---

## 引擎里没有"车"这个东西

这个引擎没有车辆约束、没有轮子关节、没有 `btRaycastVehicle`。它只有刚体、
碰撞体、求解器、射线查询、层掩码。而这几样**恰好就够**：

| 车上的东西 | 用引擎的什么做的 |
|---|---|
| 车身 | 一个动态刚体 + 一个盒子碰撞体 |
| 四个轮子 | **四条向下的射线**（`world.Raycast`），不是刚体 |
| 悬挂 | 弹簧 + 阻尼，`ApplyForceAtPoint` 加在接触点上 |
| 抓地力 | 受摩擦圆限制的冲量，`ApplyImpulseAtPoint` |
| 防倾杆 | 左右轮压缩差 -> 一对反向的力 |
| 检查点 | 触发器 + 事件回调 |
| 撞得飞的路障 | 普通动态刚体，交给求解器 |
| 轮子和门柱看得见但撞不到 | `layerMask = 0` 的碰撞体 |

### 为什么轮子是射线，不是刚体加铰链

"更真实"的做法是四个圆柱刚体、各用一个铰链接到车身上。这条路所有人都放弃过：
约束数量爆炸（四个铰链 + 四个弹簧 + 四个转向关节要在一帧里同时满足，参数稍微
不对就抖、就软、就散架）、圆柱和地面是线接触（离散求解器每帧只给一两个接触点，
过坎会卡进地面）、手感调不动（抓地力只能靠间接凑约束参数）。

所以从 Unity 的 `WheelCollider` 到 Bullet 的 `btRaycastVehicle`，主流做法都是
**射线车**。这不是简化版，是行业默认版。好处是每一项力都有名字、都能单独调：

```
悬挂 = 弹簧 + 阻尼        -> 车的软硬、侧倾、过坎、落地
侧向 = 消除侧滑的冲量      -> 抓地、转向、漂移
纵向 = 驱动 / 刹车冲量     -> 加速、刹车
  三者被同一个摩擦圆卡住   -> "油门给太猛就抓不住地"是自动出现的，没写一行
```

### 力必须按物理子步加，不能按渲染帧

FPS 那边是 `world.Step(dt)` 一把梭，引擎内部自己切子步 —— 角色控制器是运动学的，
一帧算一次没问题。车不行：车是**靠力驱动的动态刚体**，而力是在子步里被积分的。
按帧施力的话，一帧跑两个子步时第二个子步没有悬挂力，车会周期性下沉，帧率越低
越明显。所以 `RaceGame::Update` 自己跑固定步长循环：

```cpp
while (攒够一个子步) {
    vehicle.Update(world, input, h);   // 施力
    world.Step(h);                     // 只喂一个子步的时间，内部恰好跑一步
}
```

## 三个"看起来像调参、其实是算错了"的坑

这个游戏第一版能跑但完全没法看：每个弯都翻车、机器人一头撞进内圈护墙、
车在弯里毫无预兆地掉头 360 度。三个都不是参数没调好，是**判据本身错了**。

### 1. 车每个弯都翻 —— 质心太高

翻不翻由一个比值决定：

```
翻车阈值(g) = 半轮距 / 质心离地高度
```

轮胎能给的横向加速度超过它，车就是先翻、不是先滑。第一版把悬挂上端点放在车身
底部，质心离地 0.98 米、半轮距 0.79 米 —— 阈值只有 **0.8 g**，而轮胎能给 2.0 g。
差了两倍半，防倾杆加到多大都救不回来。

把悬挂上端点提到**质心上方**（`attachY = +0.28`）之后，质心离地 0.45 米、
半轮距 0.94 米，阈值 1.85 g，高于轮胎的 1.55 g —— 车在极限时先滑后翻。
真车也是这么布置的：减震塔在质心上方，发动机和乘员在下方。

### 2. 车在弯里掉头 360 度 —— 前后轮抓地力一样

前轮和后轮用同一个摩擦系数时，谁先滑完全看载荷的随机波动。打印出来的车头朝向
是 `(0.74,-0.67) -> (-0.97,-0.24) -> (+0.51,+0.86)` —— 转了一整圈。

**前轮抓地力必须低于后轮**（1.30 vs 1.75）。这是车辆动力学里最基本的一条设定：
极限时前轮先滑、车头推向弯外（转向不足），松油门就能救回来。手刹漂移则是
**临时**把后轮抓地力打到 0.28 倍，也就是临时切到"前 > 后"，松开就回来。

### 3. 机器人不会开 —— 三版进弯速度判据

- **v1：直接瞄下一个检查点。** 椭圆赛道上，检查点之间的直线是从内圈护墙里穿
  过去的。机器人一头撞进墙里，然后贴着墙磨完全程。
  → 改成沿**赛车线**做纯追踪（赛车线和护墙用同一份几何算出来，改赛道时一起变）。
- **v2：用"到前方某个点要转多少度"当弯道急缓。** 弧线的弦永远比弧本身直，
  60 米外绕过弯的点方向上可能只偏 20 度，于是 72 km/h 冲进 55 km/h 的弯。
- **v3：用前视窗口的平均曲率。** 半段直道 + 半段弯，平均下来只有弯道的一半，
  进弯速度高了 √2 倍。**均值在这里天然是错的，要的是最坏值。**
- **v4（现在）**：扫一遍前方每个点，对每个点算
  `v = sqrt(v_弯² + 2·a_刹车·s)`，取最小值。物理算出来的进弯速度。

改完之后机器人跑出 **16.50 / 13.32 / 13.32 秒**三圈，零次撞墙复位。

## 掉出赛道要放得回来，而且判据不能想当然

赛车游戏里自动复位不是"贴心"，是**必需**：翻在墙角的车是开不动的。三种情况的
判据完全不同，而两个显而易见的写法都是错的：

- **"翻了"不能只查车顶朝下**（`up.y < 0`）。最常见的一种是车斜撞护墙后**竖起来
  靠在墙上**，车顶朝侧面，`up.y ≈ 0` —— 判据说它没翻，车就永远立在那儿。
  改成 `up.y < 0.35`。
- **"卡住了"不能查速度。** 顶在墙上的车会一直小幅抖动，瞬时速度时不时窜过阈值
  把计时器清零，于是永远判不出来。改成**位移**：四秒内挪没挪过五米。
- 掉出世界立刻放回，不用等 —— 再等也只是看着它继续往下掉。

放回的位置是最后一个**合法通过**的检查点：放回起点会让跑了大半圈的人崩溃，
放回原地则会立刻再翻一次。

## 车长什么样：一层"纯装饰"的刚体

物理上车永远是**一个盒子**。画面上的车是另一组刚体：车壳（车身、前后风挡、
车顶、尾翼）和四个轮子，全都是 `layerMask = 0` 的碰撞体 —— 不和任何东西碰撞，
但渲染射线用的是单向的 `layer & mask`，照样看得见。碰撞代理比渲染模型简单，
这是所有引擎的常态（尾翼不需要参与碰撞）。

渲染时按碰撞体的**局部高度**给不同的颜色（车身红、座舱深蓝、尾翼近黑），
和 FPS 里给人形的头/躯干/腿上色是同一个办法 —— 游戏这边不用另存一张
"哪个句柄是座舱"的表。

### 轮子：薄比圆重要

第一版轮子是球。球从任何角度看都是个圆点，既看不出朝向、又和车身一样宽 ——
画面上就是四个黑球，分不清是在滚还是横着蹭。

引擎只有球 / 胶囊 / 盒，没有圆柱，而这三个都做不出"又薄又圆"：

- 胶囊沿轴向最窄也有 `2*radius`（0.6 米），做出来是个滚筒；
  把 `halfHeight` 收到 0 就退化成球，等于没改。
- 盒子的**并集只会更尖**：两个 45 度交叉的方块并起来是八角星，不是八边形。
  八边形要靠交集，而碰撞体只能并不能交。

所以结论是"薄"比"圆"重要：轮子之所以一眼能认出来，靠的是**它在车侧面立着、
很窄**这个比例，而不是它的圆度。现在一个轮子就是一块沿车身左右方向 0.26 米厚、
在前进方向上 0.62 米见方的板。

**而且它不跟着自转。** 试过让它绕轮轴转（`spinAngle` 是现成的），结果是画面上
四个菱形在原地转 —— 方块转起来看着就是方块在转，比不转更假。滚动感由车在动
本身给。

### 车身：两块斜板决定了像不像车

```
              ___尾翼___
     ______屋顶______
    /前风挡        后风挡\      <- 两块**斜**的板
___/                     \____
|   机盖        车身       尾箱 |
+----(轮)-------------(轮)-----+
```

全用轴对齐的盒子拼，座舱就是个方盒子扣在车身上，看着像面包车；前风挡一斜，
整台车立刻就"是辆跑车"了。斜板是绕 X 轴旋转的盒子：

```
R_x(θ) * (0,0,1) = (0, -sinθ, cosθ)      // 盒子默认沿 +Z "长"
```

θ 取正就把车头那端压低，正好是前风挡；后风挡方向相反，角度取负。

另一个第一版做错的比例：**座舱要几乎和车身一样宽**（0.78 对 0.92）。做窄一大圈的话，
侧面看是一大片平车顶上扣着个小盒子。

## 渲染：还是每个像素一次 `world.Raycast()`

和 FPS 那个渲染器是同一套算法（说明见 `game/Renderer.h`），共用的部分抽在
`platform/Canvas`。不共用的是"命中之后画成什么"，两边没有可复用的部分。

**路面上的白线、路肩、起点方格全是算出来的**，不是几何也不是贴图：赛道是一整块
大平板，颜色由命中点的世界坐标算出来。逐像素光线投射本来就给了每个像素精确的
世界坐标，拿来做程序化纹理是免费的。

（赛道用一整块平板、而不是一段段拼出弯道，也是有原因的：拼接处的法线会跳变，
悬挂射线打上去车会莫名其妙弹一下。赛车游戏里路面的连续性比形状重要得多。）

追车相机有三件必须做的事：

1. **挂在车的行进方向后面，不是车头朝向后面。** 漂移时两者能差四十度；跟着车头
   的话画面会转向弯心，玩家反而看不见自己正在滑向的那面墙。
2. **看向车的前方**，玩家要看的是即将到达的地方。
3. **速度越快拉得越远**——速度感主要来自这里，比屏幕上的数字管用得多。

平滑用 `alpha = 1 - exp(-rate * dt)` 而不是固定系数，否则帧率一变跟随手感就变。

## 冒烟测试

`ctest` 里的 `pe_racing_smoke` 是"机器人跑完整场比赛"，**跑不完三圈就返回 1**。

它验证的东西和 `pe_game_smoke` 完全不同，因为这个游戏用引擎的方式不同：
按物理子步施力、弹簧阻尼悬挂、摩擦圆轮胎、检查点触发器、自动复位。
"车卡在墙里"这类问题会被它测出来，而不是悄悄地跑过去。
